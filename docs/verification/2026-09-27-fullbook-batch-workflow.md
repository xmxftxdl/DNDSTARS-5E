# 全书自动导入：批量修复与集中验收

## 当前约束

2026-09-27 用户要求：不要修好一个法术或接口就调用 API 测试；先集中完成实现，在较有把握后统一验证，以降低费用。

此要求取代此前“单个法术修复 → 立即付费转换 → 单独双端验收”的推进方式。全书目标保持进行中。当前阶段不调用转换 API，也不重新提取 PDF。

现有资料清单为 155 项：95 法术、31 子职业、15 专长、14 独立特性。2026-09-27 r4 离线复核为 32 项预检通过、123 项未通过；已有 6 个指定双端流程的验收记录。与早期 33/122 不同，后来补严的施法入口校验撤销了吸收元素的旧预检通过状态。预检、指定流程验收与完整规则覆盖必须分别报告。

## 先集中完成实现

1. 复用现有 PDF 原文、提取清单、自动生成草稿和失败记录。清点全部条目及其子能力；把每个问题关联到通用机制，不按法术逐个重走开发流程。
2. 对旧的 unsupported 声明做本地核查，分为已有接口可表达、接口确有缺口、资料缺失或原文歧义、需要 DM 叙事裁定。旧模型声称“不支持”不等于引擎确实不支持。
3. 按下列机制组集中实现。一个条目可关联多组，但在总清单中只计一次：

| 机制组 | 集中处理范围 |
| --- | --- |
| 目标与区域 | 可见性、体型、关系、地面与高度、区域中心、位移与传送、地图对象资格 |
| 攻击与伤害事件 | 命中、重击、逐目标骰池、反应插入、减伤与转移、首次/每回合触发、连锁与中间结果 |
| 持续效果与资源 | 专注、回合与战役时间、休息、次数、材料、后续动作授予、叠加及结束清理 |
| 物品与召唤 | 武器/弹药绑定、临时物品、所有权与转交、召唤目录、命令、先攻与生命周期 |
| 变形与角色选项 | 属性替换恢复、子职业子能力、等级缩放、熟练与专长、能力间依赖 |
| 导入与导出 | 转换说明与接口一致性、来源证据、缓存失效、模块依赖、完整清单、安装同步与验收报告 |

4. 修复期间使用已有配置和明确标为人工编写的合成用例做本地测试。人工修复的配置不能伪装成自动转换成功证据。
5. 同一机制组完成后集中运行相关回归；类型检查在一批代码收敛后运行。检查失败后修复并重跑受影响部分，避免无改动重复启动完整检查。

## 付费转换前的条件

执行顺序固定为：机制批次实现 → 批次离线回归 → 全部待处理机制收敛 → 集中转换验证。单个法术或单个机制通过测试，不触发 API 请求。离线测试不产生模型调用费用，不必拖到所有实现完成后才运行；其作用是及时发现共享接口回归，减少最后一轮付费转换的返工。

必须先核查：

- 全部已发现的确定性机制都有实现或明确的未解决说明，不能只修完当前单项就进入付费转换。
- 通用机制的本地行为测试已通过；检查权限、资源原子扣除、刷新/重放、跨回合和效果结束等关键边界。
- SDK 类型、校验器、运行时、转换说明及导出格式已对齐。
- 155 项清单及子能力的覆盖关系已整理，外部资料校正和原文歧义保留来源，未擅自补写缺失的怪物数据或规则。
- 已生成本次待转换清单：只包含缺失或确实受接口变更影响的配置。未受影响的已验收文件继续按哈希复用。

达到以上条件后才进行集中 API 验证。不以“一个机制组刚做完”为由提前调用。

集中请求开始前保存不可变的验证清单，包含来源 ID、来源哈希、接口和转换说明版本、复用或重转原因。先完成小样本的本地预检及行为断言，再扩展本轮请求；共同失败出现时暂停后续请求，不立即付费重试。有限重试及实际使用量继续按请求记录，缓存命中不计作新的转换成功。

## 集中转换与验收

1. 固定接口和转换说明版本，先用覆盖主要机制的小样本检查转换契约；这是同一轮集中验证的起点，不恢复逐条开发时调用 API 的方式。
2. 小样本通过后运行其余待转换项。保留输入、输出、使用量、版本和断点；复用成功结果，不重新转换整本已有成功内容。
3. 若出现共同的格式或提示问题，停止该批后续付费请求，先在本地修复；不让同一问题对几十项重复收费。禁止无上限自动修复循环。
4. 每个条目都执行对应的本地规则断言；同机制的不同目标数、伤害、环级、持续时间和资源条件通过参数化测试覆盖。
5. 每种不同交互机制选代表做双端验证。共享链路不为每个法术重复启动房间；涉及不同选择、授权、反应、控制或生命周期的分支仍需独立覆盖。
6. 最后做完整模块的导出、干净环境导入、依赖完整性与双端同步验证。双端测试使用隔离房间，不修改用户 5273/5274 的现有房间。浏览器验证期间冻结代码及构建检查，避免热更新干扰。

## 进度和成本报告

原始执行绑定审计可使用 `scripts/audit-fullbook-manual-boundaries.mjs` 的 `--diagnostic` 选择具体诊断，配合 `--review <审阅快照>` 复用现有证据。工具先验证审阅的来源范围、诊断和证据，再仅按完全相同的来源 ID 与诊断文字关联；新的附加限制不会继承旧结论。输出保留原始声明、来源及审阅哈希，不修改配置，也不把“接口可表达”提升为原始转换通过。这样可以区分待重转的空配置与仍需实现的机制，避免重复开发。

离线审阅覆盖报告使用 `scripts/audit-fullbook-review-coverage.mjs --backlog <清单> --review <审阅快照> --output <新报告>`。工具核验诊断文字与哈希、条目作用域、重复审阅和证据文件，记录输入与证据文件哈希，并以独占创建方式保留报告。它不执行或认证证据中的测试，不把“已有接口可表达”改成源配置行为通过，也不会自动授权付费转换。共享诊断只对审阅明确包含的 sourceIds 生效。

条目的下一步分为：已有预检产物待验证、继续机制审阅/实现、全部现有诊断可表达后等待集中重转。最后一种仍不是转换成功，且不代替本节前述整批 API 门槛。含部分解决诊断的条目继续保留在机制审阅阶段。

分别报告：接口缺口数、预检通过数、规则断言通过数、双端交互覆盖、完整模块往返验证。不能用预检通过数作为完成数。

开发阶段新增转换 API 调用应为 0。集中验证阶段报告实际请求数和输入/输出 token，并说明哪些条目复用了缓存。发现失败时保留失败结果，不能为提高通过率隐藏条目或删除未支持声明。

外部原文核对可以解决翻译歧义，但必须保留引用并注明结果依赖补充资料，不能称为仅凭原 PDF 自动转换成功。

## 批量排程工具

### 付费验证门槛

先集中修复同类机制，复用已有原始转换产物进行本地协议检查、直接与编译入口结算测试，以及必要的隔离房间验证。单个法术修复不触发付费 API；静态预检通过也不等于源规则行为已认证。待整批接口与配置稳定后，再按来源、接口版本和既有结果选择必须重新转换的条目，一次提交受控验证批次，记录实际 token 与失败项；此前 API 门槛保持关闭。

使用 `node scripts/plan-fullbook-mechanism-batches.mjs --backlog <backlog.json> --review <review.json> --output <新的私有报告.json>` 生成离线机制批次。工具先复用审阅作用域和哈希校验，再将诊断分为具体机制/来源证据、施放入口、后续连接、执行绑定、状态提示、显式手动边界。只有已确认的固定诊断格式会进入通用类别，未知文本继续保留在机制/证据队列。

状态提示与手动边界仍然阻止验收；后者不能凭存在 DM operation 就判成叙事规则。必须检查活动正文与来源，再决定其实际机制。机制分类仅用于共同开发的排程，存在交叉，不能把分类数量相加当作独立缺口数量。一个来源的审阅不会自动推广到引用同一诊断的其他来源。

输出保留所有诊断、来源对应关系和输入哈希，独占写入新文件，不修改草稿、不生成新规则、不调用 API，也不打开付费转换门槛。已被证明可由接口表达的连接问题仍需要集中重新转换及原始条目行为验收；不能自动给孤立活动加授权或把 automation 改成 full。

### 施放入口诊断

法术预检的 `spellEntryAudit` 保存绑定活动的入口资格、拒绝原因、运行时计算的自动化等级及限制。`automation-not-full` 表示活动正文的实际处理器或手动操作仍不完整，不能靠修改 automation 标签修复；`requires-effect-grant` 表示后续活动授权限制，不能直接移除以假造初始施放。反应入口另外保留事件、施法时间与法术位契约的失败原因。入口候选通过仍不代表法术行为已验收。

该字段与既有阻断诊断并行保存，不自动修改内容或清除失败。批量分析应先区分入口结构和正文机制，避免将所有“缺少完整入口”排成简单按钮修复。

### Activity 正文原因审计

已知休息窗口诊断分流为 `source-behavior-verification`，以便批量检查实际来源的时点、目标、选项及结束条件。该类别只是排程，不证明诊断所称共享接口已完整覆盖原文；它保留全部阻断。尤其休息开始建立、休息结束清理的能力不能因存在休息完成窗口就归为实现完成。`behaviorVerificationTasks` 保留原诊断及来源范围，其他未知或附加限制文字继续进入机制审阅。

预检的 `activityMechanismAudit` 逐个保留 Activity ID、处理器覆盖分析、校验问题、显式 DM 操作的 outcome/operation ID，以及确实执行过的 Headless compatibility 检查。未执行的 compatibility 留空，不等于通过。该结构不修改原有阻断诊断和认证状态。

运行 `node scripts/audit-fullbook-activity-mechanisms.mjs <consolidated-preflight.json> <新私有报告.json>` 汇总具体处理器缺口及来源关联。每条来源优先选择已有 ready 候选，否则使用最新候选；输出保留输入哈希、解析状态、来源 ID 和 run，采用独占创建。显式 `manual-adjudication` 必须回查原文及活动正文，不能自动当成叙事，也不能删除以通过检查。没有缺少已注册组件不代表处理器支持了原文全部参数组合或完整生命周期。

### 旧提取清单的来源边界再验证

不得仅凭历史 inventory 的 complete=true 复用来源。恢复旧提取结果时仍须经过当前 finalizePdfExtractionOutput：先验证缓存全文确实位于PDF原文，再做已知下一子职标题的确定性裁切及完整性检查。不能先裁掉伪造后缀再声称全文有证据。

源边界改变会改变转换输入，旧产物必须按来源哈希重新判断复用资格。将离线恢复输出保存在新报告中，不覆盖历史清单，不把源边界通过提升为规则行为通过。等级表不能代替能力正文；仍缺少后续正文的来源必须保留在失败清单，不能静默从全书范围删除。
